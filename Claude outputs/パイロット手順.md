# パイロット実行手順（ループ設計）

対象: `docs/研究設計_生成と評価の分離.md` の §7 パイロット
期間: 2026-10（RR abstract 11-13 まで）
目的: **事前登録に書く内容を確定させること。** 論文用の結果を出すことではない。

---

## 0. ループ設計の原則

### 原則1: 1リポジトリで全部通してから広げる
Loop 1〜6 は**1リポジトリだけ**で回す。数十件集めてから壊れると回収コストが跳ね上がる。
スケールは Loop 7 まで我慢する。

### 原則2: 各ループの終わりに、人間が判断する
**生成はエージェント、判断は人。** 本研究が検証しようとしている構図を、手順自体にも適用する。
各ループには **ゲート** があり、数値を見て「進む／設計を変える／打ち切る」を人間が決める。
エージェントにゲートを通過させない。

### 原則3: 判断を先送りしない
ゲートで「あとで考える」を選ぶと、11月に全部まとめて来る。
**外れた場合の分岐を、ループに入る前に決めておく**（各ループの「外れたら」欄）。

### 原則4: 捨てられる形で作る
各ループの出力は独立したファイルに落とす。上流をやり直しても下流を作り直さずに済む形にする。

## 1. 成果物のレイアウト

```
pilot/
  config/
    agent_identifiers.yaml     # Loop 1 で確定。RR で公開する
    repos_candidate.csv        # Loop 7 で確定
    gates.md                   # 各ループの判定結果を追記していく
  raw/<repo>/
    issues.jsonl
    prs.jsonl
    reviews.jsonl
    commits.jsonl
    codeowners/<YYYY-MM>.txt   # 月次スナップショット
  interim/<repo>/
    actors.parquet             # actor_id → human/agent/legacy_bot
    modules.parquet            # (month, module, file) 展開済み
    events.parquet             # (event_id, stage, actor, module, month)
  processed/
    panel.parquet              # module × month × {H_I,H_G,H_E,A,S1..S4}
  reports/
    loop<N>_<name>.md          # 各ループの所見
```

**キャッシュ方針**: `raw/` は一度取ったら再取得しない（API レート制限対策）。
`interim/` 以降は再生成可能にしておく。

## Loop 0 — 足場

**やること**
1. GitHub API（REST / GraphQL）の認証と**レート制限の実測**
2. 1リポジトリを決めて、issue / PR / review / commit / CODEOWNERS を試験取得
3. `raw/` の保存形式を固定（jsonl、1イベント1行、取得日時を記録）

**最優先の確認**
- **review イベントが取れるか**（`requested_reviewers` ではなく、実際に提出された review）
- CODEOWNERS の履歴が取れるか（`git log` でファイル履歴を辿る）

**ゲート**
| 条件 | 判断 |
|---|---|
| review が取れる | → Loop 1 へ |
| review は取れるが requested_reviewers が取れない | → **問題なし。**本研究は「評価を誰がしたか」であって依頼は不要 |
| review も取れない | → 設計を根本から見直す。即座に相談 |

> ⚠ SES 版は Gerrit の `reviewers` 追加を「依頼」として使っていたが、**本研究に依頼は要らない**。
> 必要なのは「誰が評価したか」だけ。ここは以前の懸念より条件が緩い。

## Loop 1 — 担い手同定

**やること**
1. MSR 2026 Mining Challenge 採録論文 10 本から、エージェント同定方法を抽出
2. `config/agent_identifiers.yaml` を作る
   ```yaml
   agent:
     accounts: [...]            # 既知のエージェントアカウント
     trailer_patterns: [...]    # Co-authored-by 等に現れる識別子
   legacy_bot:
     accounts: [...]            # dependabot, renovate 等
     patterns: [...]
   ```
3. 対象リポジトリの全 actor を分類
4. **目視検証**: 各カテゴリから 50 件ずつ無作為抽出し、人手で確認

**ゲート（暫定値。実測を見て調整）**
| 指標 | 基準 | 外れたら |
|---|---|---|
| strict 分類の精度（目視） | ≥ 95% | 識別子リストを見直す |
| `agent` と判定された actor 数 | ≥ 1 | エージェントのいないリポジトリ。対象を変える |
| `legacy_bot` を `agent` と誤判定 | 0 件 | **必ずゼロにする。**混ざると結論が汚れる |

**出力**: `interim/<repo>/actors.parquet`、`reports/loop1_actor.md`（目視結果の表を含む）

> このリストは **RR で事前登録・公開する**。後から足すと「後付け」と見られる。

---

## Loop 2 — モジュール展開

**やること**
1. CODEOWNERS を月次スナップショットで取得（`git log --follow` でファイル履歴）
2. 各月について、CODEOWNERS のパスパターンをファイル集合に展開
   - 複数マッチは CODEOWNERS の規則（**後勝ち**）に従う
3. **網羅率**を測る: リポジトリ内の全ファイルのうち、どのモジュールにも属さない割合

**ゲート**
| 網羅率 | 判断 |
|---|---|
| ≥ 70% | → そのまま進む |
| 50〜70% | → 進むが、未カバー領域の扱いを明記。RR に限界として書く |
| < 50% | → **階層定義との併用を検討。**Loop 8 で方針を確定 |

**併せて記録**
- モジュール数（少なすぎると比較の検出力がない。**目安 10 以上**）
- 期間中の CODEOWNERS 変更回数（多すぎるとモジュールの連続性が問題になる）

**出力**: `interim/<repo>/modules.parquet`、`reports/loop2_modules.md`

---

## Loop 3 — 工程の帰属

**やること**

| 工程 | 帰属方法 |
|---|---|
| 生成 `G` | PR の変更ファイル → モジュール |
| 評価 `E` | その PR のモジュール |
| 意図 `I` | **リンクされた PR の変更ファイル → モジュール** |

**未決を2つ、ここで決める**
1. **跨る PR**: 変更行数最大のモジュールに寄せる（主モジュール方式）／按分する
   → **まず主モジュール方式で実装し、按分は感度分析に回す**
2. **リンクなし issue**: 除外する／本文のパス言及から推定する
   → **まず除外**。帰属率が低ければ推定を足す

**ゲート**
| 指標 | 基準 | 外れたら |
|---|---|---|
| issue のモジュール帰属率 | ≥ 50% | 30〜50% なら推定手法を足す |
| 同上 | < 30% | **3工程を断念し、生成／評価の 2 工程に縮小。**設計書 §3.3 を書き換える |
| 跨る PR の割合 | 参考値として記録 | 5 割超なら主モジュール方式の妥当性を再検討 |

**出力**: `interim/<repo>/events.parquet`、`reports/loop3_stage.md`

## Loop 4 — 指標の算出

**やること**
module × month のパネルを作り、以下を計算。

```
H_I(m,t) = 人間が作成した issue 数 / 全 issue 数
H_G(m,t) = 人間が作成した PR 数   / 全 PR 数
H_E(m,t) = 人間が提出した review 数 / 全 review 数
A(m,t)   = 1 − H_G(m,t)
```

**注意**
- 分母が 0 の月は欠測（0 ではない）。**ここを 0 にすると分布が壊れる**
- 分母が小さい月（例: 3 件未満）は別フラグを立て、感度分析で除外できるようにする

**ゲート**
| 指標 | 基準 | 外れたら |
|---|---|---|
| 有効セル（分母 ≥ 3）の割合 | ≥ 50% | モジュール粒度が細かすぎる。CODEOWNERS の粗い階層でまとめる |
| パネルの行数 | モジュール数 × 月数 に対して十分 | 期間を延ばすか対象を増やす |

**出力**: `processed/panel.parquet`

## Loop 5 — 分散の確認 ★最重要ゲート

**この研究が成立するかどうかが、ここで決まる。**

以前から懸念していた「モジュール間で差が出ないのでは」を、ここで実測する。

**やること**
1. `A(m,t)` のモジュール間分布を描く（月ごと、および全期間平均）
2. 分散を定量化
   - モジュール間の標準偏差
   - 上位 25% と下位 25% の `A` の差
   - `A > 0` のモジュールの割合

**ゲート（暫定値）**
| 条件 | 判断 |
|---|---|
| 上位25%と下位25%の `A` の差 ≥ 0.2 | → **設計通り進む。**モジュール間比較が主軸 |
| 差が 0.1〜0.2 | → 進むが検出力が不安。リポジトリ数を増やす方向で補う |
| 差 < 0.1（エージェントが均等に入っている） | → **モジュール間比較を断念。**主軸をリポジトリ間比較に切り替え、設計書 §5.1 を書き換える |
| `A > 0` のモジュールが 1〜2 個だけ | → このリポジトリでは成立しない。Loop 7 で別のリポジトリを試す |

**出力**: `reports/loop5_variance.md`（図を含む）

> **ここで外れても研究は死なない。**主軸をリポジトリ間に移せば、既存研究と同じ土俵になるぶん差別化は弱まるが、
> 「工程別の役割再配置」という問い自体は残る。**11月13日前にこれが分かることが重要。**

## Loop 6 — 分離度 4 軸

**やること**
S1〜S4 を算出し、相互の関係を見る。

| 軸 | 計算 |
|---|---|
| S1 差分型 | `H_E − H_G`、`H_I − H_G` |
| S2 集合重なり型 | `Jaccard(担い手集合_G, 担い手集合_E)` — `path_owner_overlap` の実装を流用 |
| S3 個人役割移動型 | 同一 actor の `reviewer_owner_ratio` の変化 — **既存 26 次元から流用** |
| S4 時間的先行型 | `H_G` と `H_E` の変化点推定、その前後関係 |

**見るもの**
- 4 軸の相互相関（高ければどれを主軸にしても結論は同じ → 選択の自由度が上がる）
- 各軸の分布（極端に偏っていないか、欠測が多すぎないか）
- **S4 は計算できるか**（変化点推定にはある程度の系列長が要る）

**ゲート**
| 条件 | 判断 |
|---|---|
| 4 軸が高く相関（例: ρ ≥ 0.7） | → 最も単純な S1 を主軸に。残りは副次 |
| 相関が低い | → **何を測っているかが軸ごとに違う。**解釈しやすい軸を主軸にし、差異を RR に明記 |
| S4 が計算不能 | → 副次から外す。RR に書かない |

**出力**: `reports/loop6_separation.md`

## Loop 7 — 拡大

**ここで初めてリポジトリ数を増やす。**

**やること**
1. CODEOWNERS 保有・活動量・期間条件でリポジトリを列挙
2. `A` を全期間平均で計算し、**高・中・低（ゼロ含む）の 3 層に層化**
3. 各層から N 件抽出（合計数十件）
4. Loop 1〜6 のパイプラインを全件に適用

**ゲート**
| 指標 | 基準 | 外れたら |
|---|---|---|
| パイプラインが完走するリポジトリの割合 | ≥ 80% | 落ちる原因を分類し、除外基準として明文化 |
| 各層のサンプル数 | 層あたり ≥ 10 | 条件を緩めるか、層の切り方を変える |
| Loop 5 の分散 | 全体で再確認 | 1 リポジトリの結果が偶然だった可能性 |

**出力**: `config/repos_candidate.csv`（最終リスト、除外理由つき）

---

## Loop 8 — 主軸決定と事前登録

**やること**
1. 分離度の**主軸を 1 本決める**（Loop 6 の結果から）
2. 比較設計を確定（Loop 5 の結果から：モジュール間 or リポジトリ間）
3. 工程数を確定（Loop 3 の結果から：3 工程 or 2 工程）
4. モジュール定義を確定（Loop 2 の結果から：CODEOWNERS のみ or 階層併用）
5. 設計書 §6.1 の「事前登録する / しない」の表を埋める
6. RR 原稿へ反映

**この時点で確定していなければならないもの**
- [ ] 主解析のモデル式
- [ ] 判定基準（係数の符号と有意水準）
- [ ] `agent_identifiers.yaml`（公開する）
- [ ] リポジトリ選定手順と最終リスト
- [ ] 副次解析・感度分析のリスト
- [ ] `k`（遅れ）の主値

## 3. ゲート記録

`config/gates.md` に、各ループの判定を追記していく。

```markdown
## Loop N — <名前>
実施日:
判定: 進む / 設計変更 / 打ち切り
根拠となる数値:
  - 指標A = 値
  - 指標B = 値
決めたこと:
持ち越した未決:
```

**RR の Methods は、この記録から書ける。** 「なぜこの設計にしたか」の根拠が全部残る。

## 4. 打ち切り基準

以下に該当したら、**11月13日を待たずに設計を見直す**。

| 状況 | 発見されるループ | 対応 |
|---|---|---|
| review イベントが取れない | Loop 0 | 設計を根本から見直す |
| エージェントがほぼ同定できない | Loop 1 | loose 系統を追加、または対象を変える |
| CODEOWNERS の網羅率が極端に低い | Loop 2 | 階層定義に切り替え |
| issue が PR に紐づかない | Loop 3 | 2 工程に縮小 |
| **モジュール間に A の分散がない** | **Loop 5** | **リポジトリ間比較へ主軸を移す** |

**どれも研究を殺さない。**設計が変わるだけ。早く分かることに価値がある。
