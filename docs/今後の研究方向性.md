# 今後の研究方向性

作成: 2026-09-12 ／ SES発表後の検討メモ

---

## 0. 出発点となった問題意識

現研究（SES版）には、精度以外に2つの構造的な弱点がある。

1. **「期間で予測して何が嬉しいのか」に答えられない**
   1–3か月と7–9か月を区別できることの実務的価値が説明できない。AUCでRFに負けていること以上に根本的。
2. **IRLを使っているのに報酬を解釈していない**
   逆強化学習の本来の強みである「判断基準の可読性」を一切使っていない。

この2つは、**研究の種類を「予測」から「計測」へ変えると同時に解消する**。

| | 予測研究（現状） | 計測研究（転換後） |
|---|---|---|
| 主張 | 将来の貢献を当てられる | 判断基準の変化を定量化できる |
| 評価軸 | AUC | 特徴量寄与の変化と、それを用いた推論 |
| RFに負けること | 致命的 | 無関係（RFは θ を出さない） |
| 期間分割の意味 | 不明 | **変化がいつ現れるかを見る装置**として必然 |
| AUCの役割 | 主張そのもの | **妥当性検証**（モデルが行動を説明できている根拠） |

重要なのは、**既存の実装・特徴量・原型分析・4区間設計がすべてそのまま活きる**こと。問いの立て方と評価軸が変わるだけで、コードの作り直しはほぼ発生しない。

## 0.5 逆強化学習（IRL）の看板を下ろす判断

### 査読コメントによる裏付け

SES2026の査読（ショート採録、論文ID 13）で、**3名全員がIRLを使う理由に疑問を呈している。**

| 査読者 | コメント |
|---|---|
| A-2 | 「IRL自体が内部でLSTMを用いているにもかかわらずLSTM単体との比較がなく、精度の源泉が『時系列情報の利用』か『IRLという報酬関数の定式化』かを切り分けられない。**このアブレーションがないため、IRLという手法選択の必然性を十分に裏付けられていない**」 |
| B-3 | 「**IRLを採用する利点や妥当性について理解することが困難**。RNN・LSTM・Transformerなどと比較した際のIRLの利点や位置付けを説明してほしい」 |
| C-1 | 「研究目的や**逆強化学習を採用した意図が背景・提案・評価を通して曖昧**なため、提案手法の有効性を裏付ける根拠を論文から十分に読み取れなかった」 |

**逆に、査読者が高く評価したのはIRLではない。**

- A-良1 / B-良1 / C-良1 はいずれも **アンサンブルの有意な改善** と **原型分析** を評価
- A-良2 は **ネガティブ結果の誠実な開示** を評価
- **IRLという手法そのものを評価したコメントは1件もない**

### 実装上の裏付け

コードを確認した結果、IRLとしての実質は薄い。

- 報酬ヘッドは `LSTM隠れ状態 → MLP → [R(s,0), R(s,1)]` の2ユニット出力
- 方策は各時点の2行動softmax。**soft value iteration（後ろ向きパス）を回していない**
- 損失は `Σ_t w_t·mask_t·CE(R(s_t,·), a_t)` = **重み付きcross-entropy**
- したがって R は報酬というより**将来価値を内包した soft Q値**に近く、実質は「全ステップ教師で学習した系列分類器」

さらにアブレーション（`final_step_only`）の結果は **OpenStack +3.8pp / AOSP −3.7pp** と符号が反転しており、**IRL定式化の必然性を支持しない。**

### 結論

**IRLの看板は下ろす。モデルは変えない。** 実装は「全ステップ教師の系列モデル」としてそのまま使える。失うのは名前と、それに付随する批判（MaxEnt/MaxCausalEntの別、価値反復の不在、報酬の未解釈）だけ。

## 0.6 代替の定式化

### 案1：離散時間生存解析（反復イベント）★推奨

**一文**
> 開発者の離脱と復帰を反復イベントとして捉え、時間を離散区間に分割して各区間の貢献有無を予測する。

**なぜこれが最適か**

| 現在の設計 | 生存解析での意味 |
|---|---|
| 各月 t に将来窓 W_h の二値ラベル | **離散時間生存モデルの標準形そのもの** |
| 全ステップに損失 | 正則化テクニックではなく**定式化上の必然** → A-2 / B-3 への直接の答え |
| 1年を4区間に分割 | 「いつイベントが起きるか」を見る装置 → **期間分割に必然性が生まれる** |
| 離脱・復帰が動機 | 反復イベント生存解析が正面から扱う問題 |

**査読指摘との対応**
- B-1 / C-1（目的・位置付け・手法選択の意図が不明）→ 確立した枠組みなので「なぜこの定式化か」に答えられる
- A-2 / B-3（IRLの必然性）→ 「IRLだから」ではなく「離散時間生存解析だから全ステップを使う」に変わる

**注意：この看板を出すと新しい質問が来る**
> 「ではCoxや既存の離散時間生存モデルと比較しないのか」

答え：標準的な生存解析は**一度きりの終端イベント**を扱うが、本研究の対象は離脱と復帰を繰り返す**反復イベント**。終端イベントを仮定するモデルは直接適用できない。反復イベント生存モデルとの比較は今後の課題。

**要追加文献**（現状、生存解析系の引用がゼロ。「開発者の離脱予測」で1本も引いていないのは不自然）
- Gensheimer & Narasimhan, *A scalable discrete-time survival model for neural networks*, PeerJ 2019
- van Houwelingen, *Dynamic prediction by landmarking in event history analysis*, Scand. J. Statistics 2007
- ※ 年・掲載誌は引用前に要確認

### 案2：主役を原型分析に移す

査読者3名が評価したのは原型分析と補完性の発見。**研究の主役をそこに移す。**

> 「どの手法が優れているか」ではなく、**「どの開発者タイプにどの手法が適合するか」**

- IRLは「時系列を扱う一手法」として脇に置く
- 主張は「手法の適合性は開発者タイプに依存し、それは対象ディレクトリ経験の厚みで説明できる」
- アンサンブルはその系として自然に出てくる
- 査読者が既に評価している部分を主軸にするので、**心証が良い**

### 案3：素直に系列分類器と名乗る

最も正直だが、「LSTMでレビュー参加を予測しました」だけでは新規性が薄い。**案1または案2と組み合わせる前提。**

### 推奨

**案1（生存解析）を定式化の看板に、案2（原型主軸）を主張の軸に。** 両立する。
- 定式化＝離散時間・反復イベント生存モデル → 「なぜこの設計か」に答える
- 主張＝開発者タイプによる手法適合性 → 査読者が既に評価した部分

## 0.7 IRLを外すと各方向性はどう変わるか

| 方向 | 影響 | 代替手段 |
|---|---|---|
| A（AI参入による判断変化の計測） | **ほぼ影響なし** | 「報酬 θ の変化」→「**特徴量寄与の変化**」。勾配帰属 ∂P(accept)/∂x、SHAP、permutation importance。**報酬関数と称さないぶん、むしろ主張が堅くなる** |
| A-1（予測劣化） | **影響なし** | 予測性能の劣化を測るだけなのでモデルの看板は無関係 |
| A-2（反事実） | 軽微 | 特徴量入れ替えによる反事実は、較正済み分類器なら成立する |
| B（内部表現分析） | **影響なし** | LSTM隠れ状態の分析なのでIRLと無関係。V7も使える |
| C（依頼推薦） | **最も影響を受ける** | 報酬を前提としたRL方策は組みにくい。P(承諾)×P(継続) を目的関数にする形に後退 |
| D（エージェント行動） | 影響なし | — |
| E（LLM活用） | 影響なし | — |

**結論：IRLを外して失うものはない。** 方向C（RL）はむしろ報酬を自分で設計できるぶん健全になる（0.8節）。 それ以外はそのまま成立する。むしろ「報酬関数を推定した」と主張しないぶん、計測研究としての主張は堅くなる。

## 0.8 強化学習（RL）は残す ― IRLとRLは別物

**捨てるのは「逆」強化学習だけ。** 前向きのRLはむしろやりやすくなる。

### なぜIRLを外すとRLがやりやすくなるのか

| | IRL | RL |
|---|---|---|
| 前提 | **報酬が分からない**ので行動から逆算する | **報酬を自分で定義して**方策を最適化する |
| 本研究での妥当性 | 逆算した報酬を解釈もしておらず、精度も出ていない。**使う理由が弱い** | 「モジュールの保守可能性を保つ依頼配分」は**報酬を設計できる**。逆算は不要 |

**現在の `RL/env/reward_fn.py` は IRL の R_θ をRLの報酬に流している。**

```
reward = α·π(a=1|s) + β·R_θ(s,a=1) − γ·load_penalty
```

これは**弱いIRL推定の誤差をそのままRLに引き継ぐ設計**。β項は外すべき。報酬は自分で定義する。

### 決定的な位置づけの変更：予測モデル＝環境シミュレータ

**これで「期間で予測して何が嬉しいのか」が解消する。**

| | 予測モデルの役割 | 「当てて何が嬉しいのか」 |
|---|---|---|
| 現在 | **成果物そのもの** | 答えられない |
| 変更後 | **方策を学習・評価するための環境シミュレータ** | **方策を作るために必要**。それが答え |

予測モデルは「誰がいつどのモジュールに貢献するか」を返す環境になる。方策はその上でオフラインに学習・評価する。**予測精度は「シミュレータとしての忠実度」という形で意味を持つ。RFに負けていることも、シミュレータとして十分かという議論に変わる。**

### 目的関数の設計変更

**現在**：承諾されやすい開発者に依頼を出す（+ 負荷分散）
→ 承諾率が高い人に集中するだけ。研究としての主張が弱い

**提案**：**各モジュールがレビュー可能な状態を保つ（モジュールカバレッジの維持＝バス係数を下げない）**

```
報酬 = Σ_modules 1[ 期間 W_h 内にそのモジュールへの貢献者が存在する ]
      − 負荷集中ペナルティ
      − 新規参加者の機会損失ペナルティ（任意）
```

**この目的関数にすると、既存の設計がすべて必然になる。**

| 設計 | なぜ必要か |
|---|---|
| **モジュール粒度（開発者×ディレクトリ）** | カバレッジはモジュール単位でしか定義できない |
| **1年を4区間に分割** | 各期間でカバレッジを評価するため。**期間分割の必然性がここで生まれる** |
| **将来窓の貢献予測** | 誰がいつ貢献するかを予測しないとカバレッジが計算できない |
| 原型分析 | どのタイプに依頼を出すと継続につながるかの層別 |

**現研究の弱点がすべて「RLの部品として必要だから」という形で解消する。**

### 既存資産（実装済み）

| ファイル | 内容 |
|---|---|
| `RL/env/review_assignment_env.py` | gymnasium環境。候補開発者から1人選ぶ Discrete 行動空間 |
| `RL/agent/iql.py` | Implicit Q-Learning（オフラインRL） |
| `RL/agent/bc_policy.py` | Behavior Cloning（ベースライン） |
| `RL/data/offline_dataset*.py` | オフラインデータセット構築 |
| `RL/env/state_builder.py` | 状態構築 |
| `RL/env/reward_fn.py` | **IRL依存。報酬設計を差し替える必要あり** |

**足場はすでにある。** 報酬設計と目的関数を変えるのが主な作業。

### 本物の難所：オフラインRLの評価

ここが最大の壁。**実際に依頼を出して試すことはできない**ので、方策の良し悪しを実データで確かめられない。

対策の候補：
1. **Off-Policy Evaluation（OPE）** — IPS / Doubly Robust などの標準手法。ただし行動方策（実際の依頼配分）の推定が必要
2. **シミュレータの妥当性検証** — 環境（予測モデル）が実際の挙動を再現できることを、履歴データ上で示す。**AUCがここで効く**
3. **過去の依頼配分との比較** — 実際に行われた配分を方策が再現できるか（BCベースライン）、そして提案方策がシミュレータ上でそれを上回るか
4. **保守的な主張にとどめる** — 「実運用で改善する」ではなく「シミュレータ上で、実際の配分よりカバレッジが改善する」

査読では必ず「シミュレーション上の改善に意味はあるのか」と聞かれる。**4の言い方を最初から採るのが安全。**

### AI行動変容（方向A）との関係

**両立するどころか、繋がる。**

AIエージェントの参入は、RLの観点では**環境が変わること**を意味する。すると：

- 過去のデータで学習した方策は、AI参入後の環境では最適でなくなる
- 環境シミュレータ（予測モデル）自体も陳腐化する ← **方向A-1（予測劣化）そのもの**

> 「AIエージェントの参入で環境が変化し、既存のレビュー依頼配分方策が陳腐化する。その劣化を定量化し、適応方策を設計する」

**方向AとCが1本の研究に統合できる。** AがRLの環境変化の検出、Cがそれへの適応。

### 推奨順序（改訂）

```
B（内部表現分析）          ← 着手コスト最小、IPSJジャーナル版に直結
   ↓
C'（RL: 報酬設計の変更 + カバレッジ目的）  ← 既存の足場を活かす。「何が嬉しいのか」が解消
   ↓
A-1（環境変化＝予測劣化の検出）+ E-1（AI同定）
   ↓
A+C 統合（環境変化への適応方策）
```

**C' を A より先に置く理由**：既存実装があり、データ移行（GitHub）が不要で、現研究の弱点を直接解消するため。AI要素はA以降で入る。


## 1. 先に確認すべきこと（最優先）

先生の言う「AIの行動変容」がどの意味かで、進む方向が変わる。**ここがズレたまま進めると半年後に手戻りする。**

| 解釈 | 内容 | AIの位置づけ | 対応する方向性 |
|---|---|---|---|
| (i) | AIが引き起こす人間の行動変容を**測る** | 観測**対象** | A（本命） |
| (ii) | AIを**使って**分析・研究する | **道具** | E、および A+E |
| (iii) | 研究プロセス自体をAIで回す（AIRAS / AutoRes） | **実行主体** | 別枠。既存資産はほぼ使えない |

現在検討している方向（A）では、**AIは観測対象であって道具ではない**。MSR/ICSEの実証研究としては正統だが、先生が (ii)(iii) を期待している場合は噛み合わない。

## 2. 方向性の候補

### A. AI参入によるレビュー判断の変容の計測 ★本命

**一文**
> AIエージェントの参入によって、人間開発者のレビュー受諾の判断基準がどう変化したかを、**予測モデルが依拠する特徴量寄与の変化**として、開発者タイプ別・期間別に定量化する。
>
> ※ 当初は「逆強化学習で推定した報酬関数の変化」としていたが、0.5節の通りIRLの看板は下ろす。計測手段は勾配帰属／SHAP等に置き換える。

**既存研究との差分**
- 既存（[Augmentation with Dilution](https://arxiv.org/abs/2606.26289), 11,097 repos, staggered DiD）：人間貢献者密度の低下、新規参加者 −3.7pp、レビュー需要 +5.3%
- **すべて集計統計。個人の行動軌跡はモデル化していない。**
- 本研究：集計で観測された現象を、**誰の・どの判断基準の変化として**説明する

**やってはいけないこと**
- PR提出速度、レビュー負担量そのものを測り直す → 数えれば出る指標。規模で負ける。報酬推定の道具が要らない土俵

**識別戦略の選択肢**

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| 前後比較 + DiD | AI導入前後 × 導入/非導入リポジトリ | 既存研究と同じ土俵で議論できる | 時期の交絡。DiD自体は既存研究の得意領域 |
| **同時点の対比** | 同じ期間・同じ開発者で、依頼元が人間かAIかで層別 | **時期の交絡なし。個人差も消える。既存ラベル定義がそのまま使える** | 内容の違い（AIは小さめ・定型的なタスク）が交絡 → 変更規模・ファイル数でマッチング必須 |

→ **同時点の対比を主軸に、DiDは補助**が有力。

#### A-1. 予測モデルの劣化として測る ★最初の1本はこれ

> AI導入前のデータで学習した報酬関数は、導入後に予測性能が落ちる。**その落ち方そのものを結果とする。**

例：「導入前に学習したモデルは導入後に AUC が X pp 低下する。低下は原型P1で最大、P3ではほぼゼロ」

- **反事実を仮定しない**（ホールドアウトで実測できる）
- **検証可能**（θ の変化と違い、正しさを確かめる手段がある）
- **実務的に切実**（既存の予測モデルがAI導入で陳腐化する、は運用側の本物の問題）
- **既存の予測基盤がそのまま使える。AUCも捨てなくてよい**

> **✅ 追記(2026-09-21)**: 「生成と評価の分離」研究のパイロットデータ(GitHub, 39リポジトリ)で簡易検証した(`pilot/reports/a1_prediction_decay.md`)。開発者のモジュール継続予測(ロジスティック回帰)を前半/後半で時系列分割したところ、**期待した劣化は観測されなかった**(後半の方がAUCが高い: 0.759→0.784)。最も可能性が高い理由は、パイロットの対象期間が直近12〜13ヶ月に短縮されており、「AI参入前」のベースラインを含んでいないため。**Stage2で2023-01〜直近の全期間データを使えば、意味のある検証になる可能性がある。** A-1のアイデア自体を否定する結果ではなく、「検証にはAI参入前後を跨ぐ期間設計が必須」という教訓を得た。

#### A-2. 反事実シミュレーション

報酬関数は記述統計と違い**選択のモデル**なので、反事実が計算できる。

- 「AIが書いたPRを人間が書いたものとして提示したら承諾率はどうなるか」← 特徴量の入れ替えで計算可能
- 「AI導入がなければこの開発者は残っていたか」

**最大の難所：反事実には検証の当てがない。** 「AIがなかったらこうなっていた」の正解は観測できない。シミュレーション結果の妥当性を示す手段がないまま主張すると、そこを突かれる。
→ 対策候補：LLMエージェントに開発者役をやらせて模擬軌跡を生成し、報酬関数の予測と突き合わせる（方向E-3）

#### 計測研究の妥当性をどう示すか

予測研究にはAUCという既成の評価軸があったが、計測研究にはない。**今後いちばん苦労する箇所。** 突かれるのは「その θ の変化、本当にAIのせいか」。

1. **プラセボテスト** — AI未導入リポジトリ、または導入前の同長期間で同じ分析をし、θ の変化が出ないことを示す。**最も強い**
2. **安定性** — シード・サブサンプルを変えても同じ θ の変化が再現するか（現状は単一シード。要改善）
3. **既知の事実との整合** — 推定された θ の変化が、集計で観測される現象（レビュー負担増）と辻褄が合うか
4. **内容のマッチング** — AI由来PRと人間PRで変更規模・ファイル数を揃える。`avg_change_lines` / `avg_review_size` が既にあるので材料は揃っている

#### 最終的な成果物イメージ

```
特徴量ごとの報酬重みの変化（AI導入前 → 後）

path_recency        ████▌ → ██          −大
avg_change_lines    ██    → █████▌      +大
cross_proj          ███   → ███▌        ほぼ不変
```
→ 「人間は、AIが書いたコードを『誰が書いたか』ではなく『何が書かれたか』で判断するようになった」

---

### B. 内部表現分析（現研究の深掘り）★IPSJジャーナル版の上乗せに最適

報酬ヘッドは `LSTM隠れ状態 h_t → MLP → [R(s,0), R(s,1)]`。**h_t に何が符号化されているか**を調べる。

| 施策 | 埋まる穴 | 状況 |
|---|---|---|
| ① 原型のプロービング（h_t から原型ラベルが線形に読めるか） | 「モデルは開発者タイプを獲得しているか」 | **`IRLNetworkV7_ArchetypeAux` 実装済み・未実行**（`aux_lambda>0` の出力が1件もない）。1本回すだけ |
| ② 隠れ状態空間での軌跡の可視化（PCA/UMAP） | **「離脱・復帰を捉える」という主張を評価していない問題** を直接埋める。図として映える | 未着手 |
| ③ 勾配ベースの帰属 ∂R_θ/∂x | **「IRLなのに報酬を解釈していない」問題**。θ は隠れ状態への重みなので直接読めないが、勾配なら生の37次元への寄与が出る | 未着手 |
| ④ 全ステップ版 vs `final_step_only` 版の表現比較 | 「なぜ全ステップ教師が効くのか」の機構説明。「教師信号がn倍あるだけでは」への精度以外の答え | 未着手 |

**Aに進む前にBをやる利点**：報酬を読む手段（③）は計測研究では必須。Bで手を作ってからAに入ると効率がいい。

### C. レビュー依頼推薦（介入設計）

SES版の「今後の展望」に既にある。推定報酬を環境のフィードバックとして組み込み、継続確率を考慮した依頼推薦方策を設計・評価する。

- **定義上そのまま「AIによる行動変容」**。言い方を変えるだけで繋がる
- 最も価値は高いが最も重い。オフライン評価では検証できずシミュレーションが必要
- フィードバックループの問題（推薦が行動を変え、予測が自己成就的になる）への対処が必要。承諾確率だけを最大化すると負荷集中→離脱を早める

→ **A-2 の先に置く**のが自然。単独で先行させるのは時期尚早。

---

### D. AIエージェント自身の行動モデル化（SE for AI 寄り）

開発者の欄にAIエージェントを入れ、その承諾／拒否の軌跡から報酬を推定して人間と比較する。保守可能性の問いが「来年このモジュールを見られる人がいるか」から「**人間が必要か、AIで足りるか**」に変わる。

- モジュール粒度（開発者×ディレクトリ）を持っているのは差別化になる。既存研究はほぼリポジトリ単位
- データ次第。AIエージェントの軌跡が十分に溜まったプロジェクトが必要
- Aの副産物として自然に出てくるので、独立させるより A の一部として扱うのが効率的

---

### E. LLMを道具として使う（横断的強化）

**E-1. AI由来コントリビューションの同定**
必須の前処理。正規表現では取りこぼす。MSR 2026 Mining Challenge の採録論文が全てこの問題を解いているので、**同定方法は借りる**（ゼロから考えない）。

**E-2. レビューコメントの内容を特徴量にする** ★意図と無関係に価値がある

現在の37次元は**すべてメタデータ**（件数・日数・比率・規模）。**レビューで何が言われたかを一切見ていない。**
LLMでレビューコメントを分類すれば：
- 指摘の種類（設計／スタイル／バグ／テスト）
- 指摘の深さ
- AI生成コードへの指摘は人間のものと違うか

→ メタデータでは絶対に見えない変化が測れる。**現研究の明確な弱点を埋め、かつAIを道具として使う必然性も立つ。**

**E-3. LLMエージェントによる反事実の検証**
エージェントに開発者役をやらせて模擬軌跡を生成し、推定報酬の予測と突き合わせる。「AIを使う」要求と「反事実を検証できない」穴を同時に埋める案。重い。

## 4. 推奨する順序

```
B（内部表現分析）
   ↓ IPSJジャーナル版の上乗せ。報酬を読む手段を作る
A-1（予測劣化として測る）+ E-1（AI同定）
   ↓ 検証可能な形で「変化した」を示す。1本目の論文
E-2（内容特徴量）
   ↓ メタデータの限界を超える
A-2（反事実）/ C（推薦）
   ↓ 本丸。E-3で検証手段を確保できれば
```

**理由**
- Bはコードが既にあり（V7未実行）、既存データで完結し、現研究の穴が3つ埋まる。**着手コストが最も低く、IPSJジャーナル版に直接使える**
- A-1は反事実を仮定せず実測できるので、「変化量しか示せないのでは」という批判に実測で答えられる
- A-2 / C は価値が高いが、検証手段を先に確保しないと主張が空中戦になる
